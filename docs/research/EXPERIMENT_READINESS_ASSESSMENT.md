## Перевірені обмеження runner API

`ExperimentConfig` зараз приймає `run_level` тільки `smoke`, `pilot`, `long_frame`; окремого confirmatory режиму немає. `pilot` вимагає щонайменше 20 trials/point; `long_frame` — F=20,000. `samples_per_symbol=8`, `traceback_depth=20`, `decoder_mode=finite_depth` фіксовані для цього runner. `snr_convention` допускає лише `sample_domain_complex_noise_variance`. `article_oriented` відхиляє не-identity profile, щоб не підставляти неозначені source parameters.

Поточний стандартний paired runner — A проти B0 (known-static control використовує 06B). Загальну B1 Monte Carlo інтеграцію не слід вважати наявною лише через B1 single-run GUI та окремі REPRO-08 scripts. Перед новою matched-B1 серією потрібен явний runner contract і його перевірка. Свіжа MC серія зі зміненою парою algorithms не є resume старої серії.

## Практичний допуск

**Платформа READY_WITH_LIMITATIONS для нового окремо погодженого project-defined paired дослідження.** Вона NOT_READY для обіцянки відтворити article-level 1,5 дБ чи фізичну енергетичну економію БПЛА. Наступне доцільне завдання — зафіксувати дизайн/нормалізацію/baseline/бюджет без RNG та receiver calls, див. [NEXT_SCIENTIFIC_STEPS.md](NEXT_SCIENTIFIC_STEPS.md).

Автор цього документального аудиту виконав читання файлів через PowerShell/`rg`, інспекцію API і створення документації; новий `edge_qa.json` прочитано безпосередньо. GUI/backend acceptance виконав відповідальний виконавець GUI-UX-02 у цій самій фазі, результати прив'язані до вказаних поточних artifacts. Це не самостійний запуск наукової серії автором аудиту. Фінальні поточні pytest/Ruff перевірки всієї GUI-UX-02 фази записуються її відповідальним виконавцем; до появи журналів їхнього успіху тут не заявлено.
